# Free Render + Neon deployment

render.yaml now declares one free Render Docker web service in Ohio. There are no
paid Render databases, disks, caches, workers or cron services. PostgreSQL, private
CV storage and public-media signed URLs use the existing Neon production branch.
A PostgreSQL-backed Django cache provides shared rate-limit counters without a
second free Render Key Value instance. Counter increments use database row locks.

## Configure

In Render, set these sensitive values from the ignored .env generated by neon deploy:
DATABASE_URL, DATABASE_URL_UNPOOLED, AWS_ENDPOINT_URL_S3, AWS_ACCESS_KEY_ID and
AWS_SECRET_ACCESS_KEY. The AWS_* variables connect to Neon, not AWS services.
The Blueprint sets AWS_REGION=us-east-2, NEON_STORAGE_BUCKET=uploads,
RESUME_STORAGE_BACKEND=neon and CACHE_BACKEND=database. It generates a Django key.

Brevo SMTP uses smtp-relay.brevo.com with port 2525 and STARTTLS. Render free web
services block ports 25, 465 and 587. Supply the Brevo SMTP login, SMTP key (not an
API key), and verified sender securely in Render. No credentials belong in source.

Push main and deploy the Blueprint from
https://dashboard.render.com/blueprint/new?repo=https://github.com/donfitex/talent-bridge.
The start command runs existing migrations with the direct connection, creates the
shared cache table and seeds categories, then execs Gunicorn. Free services do not
have a pre-deploy migration hook, a persistent disk or shell access. Static files
are built into the image and served by WhiteNoise. Uploaded files survive host
restarts because they live in Neon Object Storage.

## Notifications

The outbox and reminder management commands remain available, but a free Render
service cannot host the previous paid cron. Run queue_interview_reminders and
dispatch_notifications using an external scheduler with the same Neon and Brevo
configuration. Do not claim scheduled delivery until that scheduler and SMTP
credentials are configured and a real message is received.

## Verify after activation

Wait for the exact Render deploy to be live, then check HTTPS /health/, job pages,
account sessions, company/vacancy creation, a private CV upload and download,
applications and interviews. Verify object/database persistence after restart.
Neon provisioning and local HTTP checks do not themselves activate the Render web
service. No paid Render resources should be selected.

Free Render services sleep when idle and have usage limits. This is the requested
free hosting configuration; it does not carry an always-on production guarantee.
Use provider backups and test restores independently of application smoke tests.
Code rollbacks do not reverse migrations, object writes or email delivery.

## Live Render service configuration correction (2026-10-30)

The live service is https://talent-bridge-6um8.onrender.com in My Workspace.
Its original environment included `REDIS_URL=redis://redis:6379/1`, a Docker Compose hostname that is unavailable on Render. This caused signup POSTs, API throttles and readiness checks to fail. The service now uses `CACHE_BACKEND=database` and an empty `REDIS_URL`; PostgreSQL provides the shared cache and atomic authentication counters. Redis requires explicitly selecting `CACHE_BACKEND=redis` and providing a reachable private Redis URL.

Set `PRODUCTION_DOMAIN=talent-bridge-6um8.onrender.com` (hostname only) and `FRONTEND_URL=https://talent-bridge-6um8.onrender.com` (full origin, without trailing slash). FRONTEND_URL generates verification/reset links. Render's external hostname is automatically added to allowed hosts and CSRF origins. PRODUCTION_DOMAIN is a deployment label; it does not register a domain or configure DNS.

The Docker default command now runs `scripts/start.py`, so manual Render services also run direct database migrations, create the cache table and seed categories before Gunicorn starts. The Blueprint uses the same startup path.

Staff administration is `/admin/`. A superuser manages recruitment records, users and permissions, homepage/contact content under Site content, and enquiries under Contact messages. Candidate/job skill associations are included. CVs retain authorized private downloads. Contact submissions are saved to the admin inbox; this does not depend on SMTP. Staff accounts must be created with `python manage.py createsuperuser` against the intended production database; public signup never grants staff access.
